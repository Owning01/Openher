## 1 Introducción — Qué problema resuelve

La mayoría de benchmarks miden *conocimiento* (MMLU) o *código* (HumanEval). Pero un asistente general hace otra cosa: **investiga**. Busca en la web, abre un PDF, extrae una tabla, combina tres fuentes, razona sobre fechas y te da un número exacto.

GAIA propone **466 preguntas** que un humano resuelve en minutos con navegador y herramientas, pero que revientan a los LLMs si no saben usar tools. Ejemplo real del dataset: *"¿Cuál fue el % de cambio del precio de cierre de la acción X entre el 2023-01-03 y la fecha mencionada en la tabla 2 del PDF Y?"* — requiere browse + parse PDF + cálculo.

Humanos: **92%**. GPT-4 con plugins (2023): **15%**. Agentes 2025 con browsing serio: **~50%**. La brecha es el harness, no el LLM.

## 2 Ideas clave

### 2.1 Tres niveles de dificultad creciente

| Nivel | # Preguntas | Qué exige | Ejemplo |
|---|:---:|---|---|
| **L1** | 165 | 1-2 tools, 1 fuente, pocos pasos | "¿En qué año nació el autor del paper X según Wikipedia?" |
| **L2** | 216 | Multi-step, combinar 2-3 fuentes, una hoja de cálculo o PDF | "Compará dos tablas y calculá la diferencia porcentual" |
| **L3** | 85 | Investigación profunda, planning, 5+ pasos, fuentes ambiguas | "Reconstruí la cronología de un evento a partir de 4 artículos y un CSV" |

L1 valida que tu `shell/browser` y `shell/fs` funcionan. L3 valida que el agente planifica.

### 2.2 Respuesta exacta, no blanda

Cada pregunta tiene **respuesta única, corta y verificable**: un número, una fecha, una palabra, una lista corta. No hay "explicá". Se evalúa con *exact match* (normalizado) o con LLM-as-judge para casos con sinónimos. O la clavás o no. Esto hace que el benchmark sea barato de evaluar y difícil de hackear con verborragia.

### 2.3 Diseñado para resistir contaminación y atajos

- Preguntas creadas **a mano** por humanos, no scrapeadas de la web.
- Requieren **interacción con archivos reales** (PDFs, spreadsheets, imágenes) hosteados ad-hoc — no están en Common Crawl.
- Algunas respuestas cambian si buscás sin filtrar por fecha — el agente debe razonar sobre *cuándo* buscar.
- Validación humana: cada pregunta la resolvieron 2 anotadores independientes.

### 2.4 Mide tool-use en el mundo real

GAIA no es "¿sabés la respuesta?" sino "¿sabés **conseguir** la respuesta?". Evalúa:

- **Browsing** (navegar, filtrar, extraer)
- **Code execution** (calcular, parsear CSV)
- **File handling** (leer PDF, imagen, audio)
- **Multi-modal** (algunas preguntas requieren mirar una figura)
- **Planning** (ordenar pasos, backtrackear si una fuente falla)

## 3 Evidencia / Experimentos

| Sistema | GAIA Overall | L1 | L2 | L3 | Año |
|---|:---:|:---:|:---:|:---:|:---:|
| **Humanos** | **92%** | 95% | 92% | 88% | 2023 |
| GPT-4 (sin tools) | 0-5% | — | — | — | 2023 |
| GPT-4 + plugins | ~15% | ~30% | ~12% | ~5% | 2023 |
| GPT-4o + browsing | ~35% | ~55% | ~30% | ~15% | 2024 |
| Claude 3.5 + computer-use | ~42% | ~65% | ~38% | ~20% | 2024 |
| Agentes 2025 (o1, Claude 4, Deep Research) | **~50-55%** | ~70% | ~50% | ~30% | 2025 |

- **Correlación con SWE-bench baja:** un agente que lidera SWE-bench no necesariamente lidera GAIA. Son habilidades ortogonales (coding vs research). Tu thin client necesita ambas.
- **Error analysis del paper:** ~40% de fallos son *tool misuse* (no llamó al browser cuando debía), ~30% *reasoning* (leyó bien pero calculó mal), ~20% *browsing* (no encontró la fuente), ~10% *format* (respuesta correcta pero mal formateada).

## 4 Cómo aplica a opencode-remote-android — Mapeo concreto

| Concepto del paper | Dónde lo aplicás en el repo |
|---|---|
| **Browsing + multi-tool** | Tu `external_router` (mmap + probe TCP 250ms + ureq 1800ms) es el browser del paper. Si GAIA L1 te da 10% es que el proxy no extrae bien. Probá 10 preguntas L1 vía `shell.external.*` y medí. |
| **File handling (PDF/CSV/imagen)** | `fsx::read` + `HtmlPreview.tsx` (`/shell/preview/{token}/{file}` con mmap + `<base href>`) son tu handler de archivos GAIA. ¿Puede el agente abrir un PDF del dataset y extraer la tabla 2? Si no, agregá `shell.fs.read --parse-pdf`. |
| **Code execution para cálculo** | `ptyx` (:4849 WS PTY) es tu python REPL. GAIA exige calcular % y fechas — el agente debe poder hacer `python3 -c "print(...)"` vía PTY, no alucinar el número. |
| **Planning multi-step** | Las 3-5 tool calls de GAIA L2 son un mini ReAct. Tu SSE (`message.part.delta` con `type` dentro del JSON, nunca en `event:` — ver `architecture.md`) debe soportar `Thought → browse → read → exec → answer` sin perder contexto. |
| **Evaluación exacta** | Guardá en `opencode-stats` (:8765) cada GAIA run como `{question_id, level, predicted, gold, exact_match, tool_calls, latency}`. Graficá L1 vs L2 vs L3 separado — si L1 ya falla, no escales a L3. |
| **Small model local** | Phi-3 3.8B puede intentar GAIA L1 simple (1 browse + 1 read) sin modelo remoto. Entrenalo como **router**: "¿esta pregunta necesita browse o la sé de memoria?" — ahorra tokens. |

```ts
// web/src/shared/api/gaia-eval.ts — esqueleto de eval GAIA L1
type GAIAResult = { id: string; level: 1|2|3; predicted: string; gold: string; match: boolean };

async function evalGAIA(ids: string[]): Promise<GAIAResult[]> {
  const results: GAIAResult[] = [];
  for (const id of ids) {
    const q = await fetchGAIAQuestion(id); // HuggingFace dataset
    // Lanzar agente vía opencode serve :4097 con tools: shell.external, shell.fs, shell.ptyx
    const answer = await runAgent(q.question, { tools: ["shell.external", "shell.fs", "shell.ptyx"] });
    const match = normalize(answer) === normalize(q.answer);
    results.push({ id, level: q.level, predicted: answer, gold: q.answer, match });
    await logToStats({ id, level: q.level, match, tool_calls: answer.toolCalls });
  }
  return results;
}
```

## 5 Anti-patterns / Limitaciones

- **No confundas GAIA con benchmark de código.** Si tu agente pasa GAIA pero falla SWE-bench, no sirve para fixear `desktop-app`. Son complementarios. Corré ambos y no extrapoles uno al otro.
- **Browsing sin cache = flaky.** GAIA asume que la web no cambia durante la eval. Si tu `external_router` hace `ureq` sin cache ni retry, un 404 temporal te da falso negativo. Implementá retry + `cached_probe OnceLock 1500ms` (ya lo tenés — usalo también para GAIA).
- **Exact match es estricto.** "3.14%" vs "3.14 %" vs "0.0314" — el paper normaliza, pero tu script debe normalizar igual (trim, lower, strip %). Si no, vas a marcar como fallo una respuesta correcta por formato.
- **L3 es carísimo.** Cada pregunta L3 son 10-15 tool calls y 8k+ tokens. No corras 85 L3 en cada PR. Sampleá 10 L1 + 10 L2 para CI; L3 solo para release mensual.
- **Contaminación futura.** GAIA es de 2023; algunos modelos 2025 ya vieron el dataset en training. Si tu modelo remoto da sospechosamente alto en L1 (>80%), validá con preguntas GAIA-style privadas (creá 20 vos sobre tu repo/docs).

## 6 Ejercicios prácticos (en tu repo)

1. **Corré 10 GAIA L1 con tu harness y reportá.** Tomá 10 preguntas L1 del dataset (HuggingFace `gaia-benchmark/GAIA`, split validation). Lanzá tu agente con `shell.external` + `shell.fs` + `shell.ptyx` habilitados vía `opencode serve :4097`. Medí `accuracy` y clasificá cada fallo en: `browse_fail` / `reasoning_fail` / `format_fail`. ¿Cuántos fallos son porque el agente ni intentó browsear?

2. **Convertí un fallo L1 en test de regresión.** Agarrá el fallo más claro (ej: no parseó un PDF), escribí un script que reproduzca el `fs.read` + `ptyx exec` necesario, y agregalo a `web/scripts/regression-gaia.ts`. La próxima vez que toques `fsx.rs` o `external_router.rs`, ese test debe seguir pasando.

3. **Phi-3 como router de GAIA.** Entrená (o prompteá) a Phi-3 local para que, dada una pregunta GAIA, clasifique: `needs_browse | needs_calc | needs_file | trivial`. Si clasifica `trivial`, responde directo; si no, deriva al modelo grande con tools. Medí cuántos tokens te ahorrás en 20 preguntas y cuántos falsos negativos (derivó mal) pagás.
