## 1 Introducción

Antes de RAG tenías dos caminos malos: o **memorizabas todo en los pesos** (parametrizás conocimiento → modelo enorme, caro, desactualizado) o **concatenabas docs a mano** en el prompt (frágil, sin entrenamiento). RAG propone lo obvio pero bien hecho: **aprendé a buscar y a generar al mismo tiempo**.

La idea nace para tareas intensivas en conocimiento — Natural Questions, TriviaQA, FEVER — donde sin acceso a Wikipedia el modelo inventa. En vez de escalar de 400M a 11B params, RAG con 400M + índice de 21M passages le gana a T5-11B. Eso es 25× menos parámetros efectivos.

Para vos, thin client que no puede cargar `opencode.db` entera en el contexto (serían miles de tokens por sesión), RAG es el patrón base: **no metas la DB en el prompt, recuperá top-k y recién ahí generá**. Es la diferencia entre mandar 3 filas relevantes vs 10k filas que tapan el contexto y rompen el merge-only de IndexedDB v2.

> **Tesis en una línea:** entrená retriever + generador end-to-end, marginalizando sobre documentos latentes, y superás a modelos gigantes memorizadores con una fracción del costo.

## 2 Ideas clave

### 2.1 Arquitectura DPR + Seq2Seq diferenciable

RAG combina dos módulos entrenables:

| Componente | Rol | Implementación original |
|---|---|---|
| **Retriever denso (DPR)** | `p(z\|x)` — probabilidad del doc `z` dada query `x` | Bi-encoder BERT: `sim(q,d)=E_q(q)·E_d(d)`, índice FAISS (ANN) sobre Wikipedia 2018 |
| **Generador** | `p(y\|x,z)` — genera respuesta `y` condicionada a query + doc | BART-large seq2seq (400M) |

No es TF-IDF ni BM25. Son **embeddings densos** entrenados para que query y doc correcto queden cerca en espacio vectorial. FAISS permite búsqueda sub-lineal sobre 21M passages.

### 2.2 Marginalización: dos variantes

La fórmula central es:

```
p(y|x) = Σ_z p_η(z|x) · p_θ(y|x,z)
```

Donde `z` son los top-k documentos (k=5 o 10). Dos formas de marginalizar:

- **RAG-Sequence:** `p(y|x) = Σ_z p(z|x) ∏_i p(y_i | x, z, y_<i)` — *mismo doc* para toda la secuencia. Mejor para QA factoid donde la respuesta viene de un solo passage.
- **RAG-Token:** `p(y|x) = ∏_i Σ_z p(z|x) p(y_i | x, z, y_<i)` — puede **mezclar tokens** de distintos docs. Mejor para generación larga / multi-hop.

```ts
// Pseudocódigo RAG-Token (tu caso opencode.db)
const docs = await vectorSearch(queryEmbedding, k=5); // p(z|x) vía sqlite-vec
let logits = zeros(vocab);
for (const d of docs) {
  logits += d.score * generator.logits(query, d.text); // Σ_z p(z|x)*p(y|x,z)
}
const answer = decode(logits);
```

### 2.3 Entrenamiento end-to-end con señal del generador

El retriever **no se entrena solo con contrastive**. El gradiente del generador fluye al retriever: si recuperar `doc_A` ayuda a bajar loss de generación, el retriever aprende a rankearlo más alto. Sin esto, el retriever queda congelado y no mejora con la tarea downstream.

> Actualización de doc encoder fija durante training (re-indexar 21M passages cada step es inviable) — solo query encoder aprende. Truco práctico que vos replicás con `sqlite-vec`: re-embed solo queries, docs quedan estables.

### 2.4 Hot-swap sin reentrenar

Cambiar el índice (ej: Wikipedia 2018 → 2021, o en tu caso `opencode.db` de ayer vs hoy) **no requiere reentrenar el generador**. Solo re-indexás. Esto es exactamente lo que necesitás para cache merge-only: la DB externa muta, el modelo queda igual.

## 3 Evidencia / Experimentos

| Dataset | Métrica | RAG (400M) | FiD | T5-11B | SOTA cerrado |
|---|---|---|---|---|---|
| **Natural Questions** | EM | **44.5** | 41.5 | 34.5 | 44.1 (closed-book) |
| **TriviaQA** | EM | **56.1** | 55.2 | 34.9 | — |
| **FEVER** | Accuracy | **72.2** | — | 71.6 | — |
| **CuratedTREC** | EM | 55.8 | — | — | — |

**Hallazgos que importan:**

- **k=5 vs k=10:** pasar de 5 a 10 docs suma +1.5 EM en NQ, pero con rendimientos decrecientes. Para vos, `k=5` es sweet spot (latencia vs recall).
- **RAG-Token > RAG-Sequence** en tareas con respuestas largas (MSMARCO ROUGE-L +2 pts).
- **Ablación retriever congelado:** sin fine-tuning del query encoder, EM cae 4 puntos. El entrenamiento conjunto no es opcional.
- **Análisis de provenance:** en 68% de respuestas correctas el doc top-1 contenía la respuesta exacta — interpretabilidad gratis vía `p(z|x)`.

Limitación honesta del paper: asume que el índice es estático y curado (Wikipedia). Con corpus ruidoso (codebase con 10k files duplicados) la marginalización mezcla basura si no filtrás distractores.

## 4 Cómo aplica a opencode-remote-android

Tu stack ya tiene las piezas; te falta conectarlas como RAG formal:

| Concepto RAG | Tu mapeo concreto | Dónde |
|---|---|---|
| **Corpus externo** | `opencode.db` (sesiones, messages, tool_calls) servida por `opencode-stats :8765` + `web/dist` docs + `learning-raw` | `desktop-app/src/infrastructure/http/stats_router.rs` |
| **Índice ANN** | `sqlite-vec` local (embedding `all-MiniLM-L6-v2` o `bge-small`) sobre IndexedDB v2 `DB_VERSION=2` | `web/src/entities/cache/model.ts` — añade tabla `embeddings_vec` virtual |
| **Query encoder** | Embedding de la pregunta del user + últimos 20 msgs (contexto hot) | `web/src/shared/api/query.ts` |
| **Generador** | El LLM remoto (`opencode serve :4096/:4097`) condicionado con `top-k` docs inyectados al prompt | `web/src/features/session/sendPrompt.ts` |
| **Cache merge-only** | RAG evita pisar IndexedDB: solo **agrega** docs recuperados, nunca borra historial | `loadSelected` merge por id |

```ts
// Patrón RAG local que podés shippear esta semana
import { pipeline } from "@xenova/transformers";

// 1. Indexación offline (al sync de opencode.db)
async function indexSession(row: SessionRow) {
  const emb = await embedder(`${row.title} ${row.summary}`);
  await db.exec(
    `INSERT INTO vec_sessions(id, embedding) VALUES (?, ?)`,
    [row.id, emb]
  );
}

// 2. Retrieval en sendPrompt
async function ragContext(query: string, k = 5) {
  const qEmb = await embedder(query);
  const rows = await db.query(
    `SELECT id, text, distance FROM vec_sessions
     WHERE embedding MATCH ? ORDER BY distance LIMIT ?`, [qEmb, k]
  );
  // 3. Inyección al prompt con citas (previene alucinación)
  return rows.map(r => `[${r.id}] ${r.text}`).join("\n---\n");
}
```

**Regla de oro para tu harness:** nunca mandes `SELECT * FROM sessions` al LLM. Siempre `top-k` con `distance < threshold` + fallback "no hay info relevante" si `k=0`. Así respetás el `miser` de contexto y la curva en U de Lost-in-the-Middle.

## 5 Anti-patterns / Limitaciones

- **❌ RAG sin threshold → basura en el prompt.** Si el retriever devuelve 5 docs con score bajo, marginalizás ruido. Filtrá por `score > 0.7` o devolvé vacío. El paper asume índice curado; tu `opencode.db` tiene logs con `error: timeout` que no aportan nada.
- **❌ Re-embedear toda la DB cada query.** El truco RAG es encoder de docs congelado. Si re-calculás embeddings de 50k rows en el thin client, matás batería y bloqueás UI. Indexá en background con `requestIdleCallback`.
- **❌ Top-1 greedy.** RAG-Sequence demuestra que marginalizar sobre 5 docs supera top-1 por 3-4 EM. No hagas `k=1` por ahorrar tokens; perdés robustez ante retrieval imperfecto.
- **❌ Ignorar provenance.** Si no citás `[id]` de dónde salió la respuesta, no podés debuggear alucinaciones. El paper usa citas implícitas vía atención; vos hacelo explícito.
- **⚠️ Corpus desactualizado = respuestas stale.** RAG asume hot-swap fácil, pero si tu `sqlite-vec` no se regenera tras `opencode.db` mutate, respondés con data vieja. Hook `fswatch` → re-index incremental es obligatorio.
