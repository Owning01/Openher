## 1 Introducción

Tu context window es **RAM**: chica, rápida, cara. Tu historial de sesiones es **disco**: enorme, barato, lento. MemGPT formaliza esa analogía y dice: tratá al LLM como un **sistema operativo** que pagina memoria bajo demanda, no como un chatbot que recibe todo el historial concatenado.

El problema que ataca es concreto: con 8k-32k tokens de contexto, cualquier agente que intente recordar una conversación de 100k tokens (tu caso: semanas de sesiones en `opencode.db`) se queda sin espacio y empieza a truncar. Truncar = olvidar. MemGPT evita eso con **memoria virtual jerárquica + function calling + interrupts**.

La idea fuerza: el LLM mismo decide cuándo hacer `recall` (buscar en disco), `archival_search` (long-term) o `heartbeat` (chequear interrupciones), vía tools. No es el harness el que inyecta contexto a ciegas; es el **agente el que pide lo que necesita**, como un proceso que hace `mmap()`.

Para vos es directo: tu `IndexedDB v2` ya es el disco, tu `loadSelected 20/100 msgs` es la RAM. Te falta el **MemoryManager** que convierta ese truco ad-hoc en sistema operativo.

## 2 Ideas clave

### 2.1 Jerarquía de memoria en tres niveles

| Nivel | Analogía OS | Qué guarda | Tamaño | Latencia |
|---|---|---|---|---|
| **Main context** | RAM | System prompt + FIFO de últimos ~30 msgs + working memory (vars del agente) | 2k-4k tokens | Instantánea |
| **External context** | Swap | Mensajes recientes paginados (recall buffer) | 10k-50k tokens | `recall(offset, limit)` |
| **Archival storage** | Disco | Todo el historial + documentos, indexado por embeddings | Ilimitado (IndexedDB) | `archival_search(query)` |

```
┌──────────────┐  function call   ┌─────────────────┐  vector search  ┌──────────────┐
│  Main (RAM)  │ ──────────────→ │ External (Swap) │ ─────────────→ │ Archival (DB)│
│  30 msgs hot │  recall/search  │  paged msgs     │  semantic      │  IndexedDB v2│
└──────────────┘                 └─────────────────┘                └──────────────┘
        ↑ heartbeat / interrupt                                    │
        └──────────────────────────────────────────────────────────┘
```

### 2.2 Function calling como paginación

El LLM no recibe memoria infinita; recibe **tools** para gestionarla:

```ts
// Tools que MemGPT expone al LLM (vos ya tenés la mitad)
type MemoryTools = {
  // Paginación básica
  memory_recall: (opts: { offset: number; limit: number }) => Message[];
  memory_search: (opts: { query: string; top_k: number }) => Message[];
  archival_insert: (opts: { text: string }) => void;
  // Control
  heartbeat: () => "CONTINUE" | "YIELD"; // ¿hay más trabajo pendiente?
  conversation_search: (opts: { query: string }) => Message[];
};
```

El loop es: LLM genera → detecta que le falta info → llama `memory_search("error EPERM pnpm")` → sistema inyecta resultados → LLM continúa. **Autónomo**, sin que el harness adivine qué inyectar.

### 2.3 Interrupts y eventos asíncronos

Dos tipos de interrupciones que el harness puede inyectar:

- **Memory pressure:** `main context` > 90% → sistema manda `⚠️ MEMORY_WARNING: page out or summarize oldest msgs`. El LLM debe compactar o paginar.
- **External event:** nuevo mensaje del user, `time.updated` del server, o `fswatch` de `opencode.db` → `heartbeat` notifica al agente que hay trabajo.

Esto es clave para tu SSE handler: en vez de hacer polling ciego sobre `time.updated`, el agente recibe un interrupt y decide si hace `recall`.

### 2.4 Compaction con preservación de estado

Cuando la RAM se llena, MemGPT no trunca: **resume** los msgs más viejos en un summary que queda en main context. El summary preserva `role`, `intent` y `facts`, no texto literal.

```
Main antes (4k tokens, 40 msgs):
[sys][msg1..msg30][working mem]

Main después de compaction:
[sys][summary(msg1..msg20): "User pidió deploy APK, error EPERM en pnpm..."][msg21..msg30][working mem]
```

Costo: 1 call extra al LLM para resumir, pero ahorra 2k tokens por turno.

## 3 Evidencia / Experimentos

| Benchmark | Tarea | MemGPT | Baseline (truncation) | Ganancia |
|---|---|---|---|---|
| **Nested Key-Value** | Recuperar valor con clave anidada a 10k distancia | **92%** | 41% | +51 pts |
| **Conversation QA** | Preguntas sobre diálogo de 50k tokens | **84%** | 52% | +32 pts |
| **Deep memory retrieval** | Hecho mencionado 1 vez hace 100 msgs | **78%** recall | 23% | 3.4× |
| **Multi-session coherence** | Mantener persona consistente tras 20 sesiones | 4.2/5 human rating | 2.8/5 | +50% |

**Ablaciones relevantes:**

- Sin `archival_search` (solo recall FIFO): recall cae de 78% → 45%. El search semántico es load-bearing, no el paginado secuencial.
- Sin `heartbeat`: latencia de respuesta a eventos +2.3s (polling). Con heartbeat, reacción < 300ms.
- Context 4k vs 16k: MemGPT con 4k + paging iguala a baseline con 16k flat. **No necesitás contexto gigante si paginás bien.**

## 4 Cómo aplica a opencode-remote-android

Ya tenés el 70% armado. Falta formalizarlo como OS:

| Concepto MemGPT | Tu implementación actual | Qué falta |
|---|---|---|
| **Main context (RAM)** | `loadSelected` con 20 msgs hot + system prompt | Definir `MAX_MAIN_TOKENS=3500` y medir uso real |
| **External context** | `loadSelected` con 100 msgs al abrir sesión | Exponer como `memory_recall(offset, limit)` tool al LLM, no precarga fija |
| **Archival storage** | `IndexedDB v2` merge-only con `DB_VERSION=2` + `opencode.db :8765` vía `stats_router.rs` | Añadir índice vectorial `sqlite-vec` para `archival_search` |
| **Memory pressure** | `miser` trunca a 20 msgs si > limit | Reemplazar truncado por `compaction` (resumen) + `MEMORY_WARNING` interrupt |
| **Heartbeat** | Polling `time.updated` cada 2s | Cambiar a `heartbeat` tool + SSE `session.next.*` como interrupt |

```ts
// Implementación MemoryManager para tu harness
class MemoryManager {
  private MAIN_LIMIT = 3500; // tokens
  private ARCHIVAL_DB = "opencode-v2"; // IndexedDB v2

  async checkPressure(mainTokens: number): Promise<void> {
    if (mainTokens > this.MAIN_LIMIT * 0.9) {
      // No trunques: compactá
      const oldest = await this.getOldest(10);
      const summary = await this.summarize(oldest); // 1 LLM call
      await this.replaceInMain(oldest, summary);
      this.emitInterrupt("MEMORY_WARNING_RESOLVED");
    }
  }

  // Tools que exponés al LLM remoto vía opencode serve
  tools = {
    memory_search: async (q: string) => {
      const emb = await embed(q);
      return this.archival.search(emb, 5); // sqlite-vec MATCH
    },
    memory_recall: async (offset: number, limit: number) => {
      return this.archival.paginate(offset, limit); // merge-only, no delete
    },
  };
}
```

**Flujo target en `web/src/features/session`:**

1. User manda prompt → `MemoryManager` estima tokens de main.
2. Si `>90%`, compacta antes de `sendPrompt`.
3. Durante `SSE stream`, si LLM llama `memory_search`, el harness intercepta, hace `sqlite-vec` local, inyecta results y reanuda stream.
4. `cache merge-only` garantiza que `archival_insert` nunca pisa historial: solo `put` por `id`, jamás `clear`.

## 5 Anti-patterns / Limitaciones

- **❌ Precargar 100 msgs siempre.** Es RAM desperdiciada si el user pregunta algo del principio del historial. MemGPT carga bajo demanda; vos cargás fijo 100 y pagás tokens aunque no uses. Medí: ¿cuántos de esos 100 son realmente citados en la respuesta? Si < 10%, es overhead puro.
- **❌ Truncar sin resumir.** Tu `miser` actual corta a 20 msgs y tira el resto. Perdés `intent` del user de hace 30 msgs. MemGPT demuestra que compaction preserva 84% de recall vs 52% con truncation. No tires, resumí.
- **❌ Polling ciego en vez de heartbeat.** Hacer `fetch time.updated` cada 2s cuando el LLM está generando es ruido. El interrupt debe ser event-driven (SSE `session.next.*`), no polling.
- **❌ Exponer toda la DB como tools.** Si le das al LLM `SELECT * FROM sessions WHERE ...` sin límite, puede pedir 10k rows y reventar contexto. Siempre `LIMIT` + `distance threshold` en `archival_search`.
- **⚠️ Compaction recursiva infinita.** Si resumís un resumen, perdés detalle exponencialmente. Guardá `original_ids` en el summary y permití `recall` del original si el LLM lo pide explícito.

## 6 Ejercicios prácticos

1.  **MemoryManager mínimo (3h):** Implementá `checkPressure()` que mida tokens de `loadSelected` (usa `tiktoken` o conteo `~4 chars/token`). Si pasa 3500, tomá los 10 msgs más viejos, resumilos con el LLM (`"Resumí estos 10 msgs en 100 tokens preservando facts"`), reemplazalos en main. Medí tokens ahorrados y recall de un hecho del inicio.
2.  **Tool `memory.search` (2h):** Exponé `memory_search(query)` como tool vía `opencode serve` (o simulado local). Indexá 50 sesiones de `opencode.db :8765` con embeddings. Pedile al LLM que responda "¿qué error tuvimos en el deploy del martes?" y verificá que llame a `memory_search` en vez de alucinar.
3.  **Benchmark truncado vs MemGPT (1h):** Sobre 20 sesiones reales, compará: (a) truncar a 20 msgs, (b) MemGPT con compaction + search. Preguntá 10 facts del inicio/medio/fin y medí accuracy. Esperás curva en U en (a) y flat en (b) — validá Lost-in-the-Middle.
