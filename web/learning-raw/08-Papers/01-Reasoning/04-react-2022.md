## 1 Introducción — Qué problema resuelve

Hasta 2022 había dos escuelas separadas:

- **CoT (Chain-of-Thought):** el modelo razona en texto, pero no toca el mundo. Puede alucinar datos que no existen.
- **Act (tool use):** el modelo llama herramientas, pero sin razonar antes. Elige tools a ciegas y se pierde.

ReAct las combina: intercala **Thought → Action → Observation** en loop. El `Thought` razona sobre qué hacer y por qué; el `Action` ejecuta una herramienta; la `Observation` trae verdad del mundo que alimenta el próximo `Thought`. Es el loop que usás cada vez que el agente hace `shell.fs.ls` → ve el listado → decide `shell.fs.read`.

El paper demuestra que ReAct supera a CoT solo y a Act solo en HotpotQA, FEVER y AlfWorld (simulación doméstica), y además es más interpretable y depurable porque cada `Thought` explica la decisión.

## 2 Ideas clave

### 2.1 El formato exacto — Thought, Action, Observation

El prompt few-shot enseña este DSL con ejemplos:

```
Thought: Necesito verificar si el archivo de config existe antes de editarlo.
Action: shell.fs.ls({"path": "web/public/learning"})
Observation: ["manifest.json", "docs/"]

Thought: Existe. Ahora leo el manifest para ver la estructura actual.
Action: shell.fs.read({"path": "web/public/learning/manifest.json"})
Observation: {"version": 2, "docs": [...]}

Thought: Ya tengo el contenido. Voy a agregar la nueva entrada al manifest.
Action: shell.fs.write({"path": "web/public/learning/manifest.json", "content": "..."})
Observation: {"ok": true}
```

Reglas:

- **Siempre Thought antes de Action.** Sin Thought explícito, el modelo alucina tool calls con parámetros incorrectos.
- **Observation es texto del harness, no del modelo.** El modelo no inventa observations — las recibe.
- **El loop termina con `Finish: <respuesta>`** cuando el agente cree que completó la tarea.

### 2.2 Por qué Thought importa — Guía y corrección

El `Thought` cumple dos funciones que Act solo no tiene:

1. **Descompone la tarea:** "primero listo, luego leo, luego edito" — planifica sin ejecutar.
2. **Corrige con observations:** si `ls` devuelve vacío, el próximo `Thought` dice "no existe, debo crearlo" en lugar de insistir con `read`.

En AlfWorld (tareas domésticas simuladas), ReAct logra **34% success vs 26% Act-only** — la diferencia es puro razonamiento intermedio.

### 2.3 ReAct + CoT — Lo mejor de ambos mundos

El paper propone ReAct+CoT: dentro de cada `Thought`, el modelo hace CoT (razona paso a paso) antes de elegir `Action`. En HotpotQA, ReAct+CoT supera a ReAct puro. Para tu harness: cada `Thought` debería ser un mini-CoT de 2-3 pasos, no un "voy a hacer X" escueto.

### 2.4 Interpretabilidad y debugging

Human study del paper: anotadores prefieren trazas ReAct porque pueden ver *por qué* el modelo eligió cada tool. Para vos esto es oro: cuando un agente hace 5 `tool_call` seguidos sin sentido, con ReAct podés leer los `Thought` y detectar dónde se perdió.

## 4 Cómo aplica a opencode-remote-android — Mapeo concreto

Tu thin client YA es ReAct. Solo falta tiparlo y pulirlo:

| Concepto ReAct | Mapeo en tu repo |
|---|---|
| **Thought** | `message.part.delta` con `type: "reasoning"` → renderizado en `ThinkingBlock` colapsable. Cada `Thought` debe ser CoT de 2-3 pasos, no un título. Ver `web/src/widgets/ThinkingBlock.tsx`. |
| **Action** | `type: "tool_call"` → `shell.fs.*`, `shell.ptyx.*`, `shell.external.*`, `shell.scm.*`. Tipá `type ReActAction = { tool: string; input: Record<string, unknown> }` en `web/src/shared/sse/handler.ts`. |
| **Observation** | `type: "tool_result"` → lo que devuelve el harness Rust (`fs_router.rs`, `ptyx :4849`, `external_router.rs`). Debe ser **estructurada** (JSON con `ok/error/data`), no texto libre, para que el próximo Thought la use bien. |
| **Loop** | Tu `useSSEHandler` / `useMessages` ya hace el loop. Agregá log de tripleta `ReActTurn = { thought, action, observation }` por turno para devtools. |
| **Finish** | Cuando el modelo emite `Finish: <respuesta>` o deja de llamar tools, tu `loadSelected` hace merge incremental por `id` en IndexedDB v2. El mensaje optimista no se remueve — lo confirma `loadSelected` por match de texto. |
| **System prompt** | Forzá el formato en el prompt del sistema: `Thought: ... → Action: ... → Observation: ... → ... → Finish:`. Sin este template, el modelo genera `Action` sin `Thought` y pifia parámetros. |

```ts
// web/src/shared/sse/handler.ts — tipado ReAct explícito
type ReActPart =
  | { type: "reasoning"; text: string }   // Thought (CoT)
  | { type: "tool_call"; tool: string; input: Record<string, unknown> } // Action
  | { type: "tool_result"; tool: string; output: unknown }              // Observation
  | { type: "finish"; answer: string };

type ReActTurn = {
  thought: string;
  action: ReActPart & { type: "tool_call" };
  observation: ReActPart & { type: "tool_result" };
};

// En el system prompt (shared/api/prompts.ts):
const REACT_SYSTEM = `
Formato obligatorio — alterná siempre:
Thought: [razoná en 2-3 pasos qué hacer y por qué]
Action: shell.fs.read({"path": "..."})  // UNA tool por turno
Observation: (te la da el harness, no la inventes)
... repetí hasta ...
Finish: [respuesta final al usuario]
Si omitís Thought antes de Action, tu tool call será rechazado.
`.trim();
```

**UI sugerida:**

- `Thought` → bloque colapsable con ícono 🧠, como tu `ThinkingBlock` actual.
- `Action` → badge con nombre de tool + status (`probe 250ms` de `external_router.rs:19`).
- `Observation` → preview truncado (primeras 5 líneas) expandible.
- DevTools: tabla de `ReActTurn[]` por sesión para auditar cuántos turnos tomó cada tarea.

## 5 Anti-patterns / Limitaciones

- **No uses ReAct para tareas triviales.** Para `/help`, `list_dir` simple o `fs.read` directo, el loop `Thought → Action → Observation` es overhead. Usá workflow determinista (una tool call directa sin Thought). Anthropic lo dice claro en *Building Effective Agents*: no todo necesita agente.
- **Observations no estructuradas matan el próximo Thought.** Si tu `fs_router.rs` devuelve texto libre `"Error: file not found"` en lugar de `{ ok: false, code: "ENOENT", path: "..." }`, el modelo no puede razonar bien sobre el error. Estructurá todas las observations.
- **Thought escueto = Act con extra steps.** Si el modelo genera `Thought: voy a leer el archivo` sin descomposición, no estás ganando nada sobre Act. Forzá CoT dentro del Thought: `1) qué sé 2) qué falta 3) qué tool lo da`.
- **Loop infinito sin Finish.** Sin criterio de parada, el agente puede hacer 20 `Thought → Action` sin terminar. Poné `max_turns = 15` y un `Finish` forzado si se excede, guardando estado en IndexedDB v2 para retomar.
- **SSE y ReAct desalineados.** Tu `message.part.delta` con `partID` es el stream del decoder; si no mapeás `part.type` a `ReActPart`, mezclás reasoning con tool_call en el mismo string y perdés la estructura. Tipalo.
