## 1. Introducción

Si Toolformer enseña 5 tools y Gorilla evalúa 1.600, ToolLLM va al extremo: **16.000 APIs reales de RapidAPI**, con diálogos multi-step generados por ChatGPT y un modelo propio (ToolLLaMA) que supera a GPT-4 en tareas que encadenan varias llamadas. ¿Cómo? Cambiando el algoritmo de búsqueda: en vez de ReAct lineal (intento → fallo → sigo), usa **Depth-First Search sobre el árbol de decisiones de APIs** — explora una rama, si falla hace backtrack y prueba otra, como un Tree-of-Thoughts pero en espacio de herramientas.

El paper aporta dos cosas: **ToolBench**, el dataset/benchmark de 16k APIs con ToolEval (pass rate + win rate), y la receta para entrenar un modelo que no se queda atascado en el primer error. Para tu app, donde `external_router.rs:19` maneja 5 plugins con `probe()` 250ms y `cached_probe` 1500ms, la lección es directa: tu harness no puede ser lineal; necesita backtracking y fallback cuando `screenshots :3002` o `opendesign :3000` no responden.

## 2. Ideas clave

| Idea | Qué significa | Por qué supera a ReAct lineal |
|---|---|---|
| **DFS decision tree** | Cada nodo es una llamada a API; si falla, backtrack y prueba otra rama | No se rinde al primer error; explora alternativas |
| **Neural API retriever** | Dado el intent, recupera top-k APIs relevantes (no las 16k) | Hace viable el contexto; sin esto, imposible |
| **ToolBench generation** | ChatGPT genera diálogos multi-step diversos cubriendo las 16k APIs | Dataset a escala sin anotación humana masiva |
| **ToolEval** | Mide pass rate (¿resolvió?) + win rate (¿camino eficiente vs GPT-4?) | No alcanza con resolver; importa costo y pasos |

```
ReAct lineal:  intent → call A → falla → call A de nuevo → falla → abandono
ToolLLM DFS:   intent → call A → falla → backtrack → call B → ok → call C → éxito
                          ↘ call B (alternativa ya explorada en otra rama)
```

```python
# Pseudocódigo DFS de ToolLLM (simplificado)
def dfs(state, depth=0):
    if is_terminal(state): return evaluate(state)
    apis = retriever.retrieve(state.intent, top_k=5)
    for api in apis:
        result = execute(api, state)
        if is_error(result):
            continue  # backtrack implícito: prueba siguiente API
        next_state = apply(state, api, result)
        score = dfs(next_state, depth+1)
        if score.passed: return score
    return failure(state)
```

**Diferencia con Gorilla:** Gorilla optimiza *selección* de una API; ToolLLM optimiza *secuencia* de APIs con recuperación de errores. Son complementarios.

## 3. Evidencia y experimentos

| Benchmark | ToolLLaMA (DFS) | GPT-4 (ReAct) | ChatGPT | Comentario |
|---|---|---|---|---|
| **ToolBench pass rate** | **supera GPT-4** | baseline | inferior | DFS + retriever ganan en multi-step |
| **ToolBench win rate** | superior | — | — | Camino más eficiente (menos calls fallidas) |
| **APIs no vistas (generalización)** | competitivo | — | — | Retriever ayuda a generalizar fuera del training |
| **Ablation sin DFS (solo ReAct)** | cae 10-15 pts | — | — | El backtracking es el diferencial |

- **Generación de datos:** ToolBench usa ChatGPT para sintetizar diálogos multi-step que cubren combinaciones de APIs — sin esto, no hay forma de cubrir 16k APIs con anotación humana.
- **Retriever:** sin retriever, el modelo ve descripciones truncadas o se queda sin contexto; con retriever top-k, accuracy sube y costo baja.
- **Costo de DFS:** más llamadas exploratorias que ReAct lineal, pero el win rate muestra que el camino final es más eficiente porque evita reintentos ciegos.

## 4. Cómo aplica a opencode-remote-android

Tus 5 plugins externos son tu "RapidAPI" local. Hoy tu harness es lineal: `probe()` → si falla, error al usuario. ToolLLM te dice que eso no escala.

| Concepto ToolLLM | Mapeo concreto en tu repo |
|---|---|
| **DFS + backtrack** | Si `screenshots :3002` falla (probe 250ms timeout), no devuelvas error: hacé backtrack y probá fallback — `cached_probe` 1500ms, reintento `ureq 1800ms`, o plugin alternativo. Registrá el fallo en OTel span. |
| **Neural retriever** | Implementá BM25/dense en `shared/api/retriever.ts` sobre tus 25 tools. Dado "editá un archivo", retrievea `fs.read`, `fs.write`, `pty.exec(cargo check)` — no `screenshots` ni `vioeditor`. Ahorro 2-3k tokens/turn. |
| **ToolBench → tu bench** | Armá `toolbench-mini` con 20 tareas multi-step reales: `view→edit→lint→run`, `git.status→diff→commit`, `preview mmap+base href`. Medí pass/win rate. |
| **hyper :4850 mmap + tiny_http :4848** | Cada intento DFS que toca `hyper :4850` (estáticos) o `tiny_http :4848` (API) debe ser idempotente y logueado; el backtrack no debe dejar estado corrupto. |
| **WS ptyx :4849** | `pty.exec` es tu tool más riesgosa para DFS — cada rama que ejecuta un comando debe estar sandboxed y con timeout; si no, el DFS puede colgar el harness. |
| **external_router.rs:19 split_cmd** | El router debe soportar reintentos sin re-spawnear proceso cada vez: `probe()` decide si reintentar o hacer backtrack a otra tool. `split_cmd` + `CREATE_NO_WINDOW` no deben re-ejecutarse en cada rama fallida. |

```typescript
// shared/api/retriever.ts — idea mínima BM25 para tu harness
import { tools } from "./tools.js"; // 25 tools con description

export function retrieveRelevantTools(intent: string, topK = 5) {
  // Score BM25 simple sobre description + name
  return tools
    .map(t => ({ tool: t, score: bm25(intent, t.description) }))
    .sort((a, b) => b.score - a.score)
    .slice(0, topK)
    .map(r => r.tool);
}
// En cada turno: solo esos topK van al system prompt → -70% tokens
```

```rust
// desktop-app/src/infrastructure/http/external_router.rs — backtrack conceptual
// Si probe falla, no retornes 503 de inmediato: intentá fallback antes de rendirte
if !probe(&addr, Duration::from_millis(250)) {
    if let Some(cached) = cached_probe(&name) { /* usa cache 1500ms */ }
    else if retry_with_backoff(|| ureq_get(&url, Duration::from_millis(1800))).is_ok() { /* ok */ }
    else { return dfs_backtrack_to_alternative_tool(); }
}
```

> **Regla de oro:** un harness lineal falla al primer plugin caído. Un harness DFS backtrackea y resuelve igual — esa es la diferencia entre demo y producción.

## 5. Anti-patterns y limitaciones

| Anti-pattern | Por qué duele | Qué hacer en cambio |
|---|---|---|
| **ReAct lineal sin backtrack** | Un `probe()` fallido mata toda la tarea multi-step | DFS: si una tool falla, probá la siguiente rama |
| **Mandar las 25 tools siempre** | Costo + confusión + hallucination | Retriever top-k por intent |
| **Reintentar la misma tool indefinidamente** | Loop infinito si el plugin está caído | Backtrack a tool alternativa tras 1-2 reintentos con backoff |
| **Sin ToolEval (solo pass/fail)** | No ves si tu harness hace 8 calls cuando bastan 3 | Medí win rate / eficiencia de camino |

**Limitaciones del paper:**

- DFS explora más ramas → más costo de inferencia que ReAct lineal. Requiere presupuesto de calls y timeout por rama.
- ToolBench se genera con ChatGPT — puede tener sesgo hacia patrones que ChatGPT ya conoce; no es "ground truth" humano perfecto.
- No cubre seguridad: backtracking sobre tools con efectos secundarios (ej: `fs.delete`, `git.push`) sin sandbox es peligroso. Ver `07-Seguridad/01-mcptox-2025.md`.

## 6. Ejercicios prácticos

### Ejercicio 1 — Medir ahorro del retriever (30 min)
1. Implementá `retrieveRelevantTools(intent, topK=5)` con BM25 sobre tus 25 tools.
2. En 20 tareas reales, medí tokens de system prompt con 25 tools vs top-5. Graficá ahorro vs accuracy (AST match).
3. Probá k=3,5,7 y elegí el óptimo para tu app.

### Ejercicio 2 — DFS vs ReAct lineal (60 min)
1. Tomá 5 tareas multi-step (ej: "creá un archivo, editalo, verificá con cargo check").
2. Implementá dos modos: ReAct lineal (si falla, reintenta mismo call) vs DFS (si falla, backtrack a tool alternativa).
3. Medí pass rate, número de calls y latencia p95. Reportá win rate.

### Ejercicio 3 — Fallback de probe (20 min)
1. Simulá caída de `screenshots :3002` (bloqueá el puerto).
2. Verificá que tu harness haga: `probe 250ms` → `cached_probe 1500ms` → `ureq 1800ms` → backtrack sin crashear.
3. Instrumentá con OTel span `tool.call { name, error, retry_count }`.
