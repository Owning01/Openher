## 1. Introducción

MCP (Model Context Protocol) es el intento más serio de estandarizar lo que hoy cada harness hace a mano: **descubrir herramientas, negociar capabilities, invocarlas con validación y auditar el uso**. Anthropic lo lanzó en noviembre 2024 como protocolo abierto — inspirado explícitamente en LSP (Language Server Protocol) — y lo donó a la Linux Foundation en diciembre 2025. Si LSP unificó cómo los editores hablan con language servers, MCP quiere unificar cómo los LLMs hablan con tools.

Hoy tu `desktop-app/src/infrastructure/http/external_router.rs:19` hace `split_cmd()` + `probe()` TCP `250ms` + `ureq 1800/700ms` + `cached_probe 1500ms` por cada plugin externo (`opendesign :3000`, `screenshots :3002`, `vioeditor :1420`, etc.). Cada plugin nuevo requiere código nuevo, sin schema, sin permisos, sin discovery. MCP reemplaza ese acople con un handshake estándar: el client pregunta "¿qué tools exponés?", el server responde con lista + JSON Schemas, y cada invocación se valida contra el schema.

El survey de Hou et al. (2025) complementa la spec con el análisis de **16 categorías de amenazas** — porque discovery dinámico sin seguridad es un tiro en el pie (ver `07-Seguridad/01-mcptox-2025.md`).

## 2. Ideas clave

| Concepto MCP | Qué es | Analogía LSP |
|---|---|---|
| **Handshake `initialize`** | Client manda `initialize` con capabilities; server responde con `tools/list` + `resources/list` + `prompts/list` | `initialize` de LSP que negocia features |
| **`tools/call`** | Invocación validada por JSON Schema: `tools/call { name, arguments }` | `textDocument/completion` validado |
| **Resources** | Servers exponen docs/context como recursos tipados (ej: `opencode.db`, `learning/`) | `workspace/symbol` |
| **Sampling** | Server puede pedir al client que llame a un LLM (para subagentes) | No tiene analogía directa — es delegación |
| **Transports** | stdio, SSE, Streamable HTTP | LSP usa stdio/JSON-RPC; MCP igual |

```json
// Handshake MCP (simplificado)
→ Client: { "jsonrpc": "2.0", "method": "initialize", "params": { "capabilities": {} } }
← Server: { "capabilities": { "tools": {}, "resources": {} },
            "tools": [{ "name": "shell.fs.read", "inputSchema": { "type": "object", "properties": { "path": {"type": "string"} } } }] }

→ Client: { "method": "tools/call", "params": { "name": "shell.fs.read", "arguments": { "path": "web/src/App.tsx" } } }
← Server: { "content": [{ "type": "text", "text": "contenido..." }] }
```

**Por qué importa para vos:**

```
Hoy (acoplado):   agregar plugin → editar external_router.rs → nuevo if → nuevo probe → redeploy
Con MCP (desacoplado): agregar plugin → plugin corre como MCP server → discovery automático → cero código en router
```

## 3. Evidencia y estado del ecosistema

| Aspecto | Estado 2025-26 | Fuente |
|---|---|---|
| **Adopción** | Anthropic, OpenAI, Cursor, Zed, Windsurf, SDKs TS/Python/Rust | modelcontextprotocol.io |
| **Servers públicos** | 100+ community servers (filesystem, github, slack, postgres, etc.) | github.com/modelcontextprotocol/servers |
| **Seguridad** | 16 amenazas catalogadas; tool poisoning ASR 72.8% sin defensas | Hou et al. 2503.23278 + MCPTox 2508.14925 |
| **Donación a LF** | Dic 2025, gobernanza abierta | Linux Foundation announcement |

- **No es paper con benchmark tradicional** — es una spec de protocolo. La "evidencia" es adopción y el survey de seguridad que valida que el problema es real.
- **Hou et al.** sistematiza amenazas: tool squatting, prompt injection vía `description`/`resource`, exfiltración vía `tool_result`, privilege escalation. Cada una con mitigación propuesta (allowlist, manifest firmada, sandbox).
- **MCPTox** (ver `07-Seguridad/01-mcptox-2025.md`) confirma empíricamente: sin defensas, ASR 72.8% con solo envenenar `description`.

## 4. Cómo aplica a opencode-remote-android

| Concepto MCP | Mapeo concreto en tu repo |
|---|---|
| **`external_router.rs:19 split_cmd` → MCP servers** | Cada plugin (`opendesign`, `screenshots`, `vioeditor`, `informes :5174`, `widgetnotas`) corre como MCP server independiente. El router se vuelve un **MCP client** que hace `initialize` y descubre tools dinámicamente. Cero `if path ==`. |
| **`probe() 250ms` → `initialize` + health** | En vez de TCP connect crudo, el health check es `tools/list` via MCP. Si el server responde, está vivo y sabés qué tools tiene. `cached_probe 1500ms` se reemplaza por cache de `tools/list`. |
| **`ureq 1800/700ms` → `tools/call`** | Cada invocación va por `tools/call` validada por `inputSchema`. No más args mal tipados que dan 400 en `sendPrompt v2`. |
| **`tiny_http :4848` + `hyper :4850 mmap`** | Exponé `shell.fs.*` y `shell.git.*` como MCP servers en Rust. `hyper :4850` sirve estáticos con `mmap+br`; el MCP server expone `resources` para esos archivos. |
| **`WS ptyx :4849`** | `pty.exec` como MCP tool con `inputSchema { cmd, cwd, timeout }` y output estructurado `{ stdout, stderr, exitCode }`. El LLM no construye shell crudo. |
| **`mmap+<base href>` para embeds** | `vioeditor`/`informes` se sirven vía `mmap` con `<base href="/shell/external/<name>/embed/">` inyectado; como MCP resource, el HTML ya viene con base href y evita 404 de `/assets/*`. |
| **`opencode-stats :8765`** | Exponé `opencode.db` como MCP resource — el agente puede consultar stats sin HTTP ad-hoc. |
| **Seguridad** | Implementá allowlist: el usuario aprueba qué tools puede llamar cada server. No auto-discover todo. Ver `01-mcptox-2025.md` para defensas concretas. |

```rust
// desktop-app/src/infrastructure/http/mcp_router.rs — idea de migración
// En vez de if path == "/shell/external/..." → MCP client genérico
pub async fn handle_mcp_call(req: McpRequest) -> McpResponse {
    let server = mcp_registry.get(&req.server_name)?; // discovery dinámico
    let tool = server.tools.iter().find(|t| t.name == req.tool_name)?;
    validate_against_schema(&req.arguments, &tool.input_schema)?; // ← validación automática
    server.call_tool(req.tool_name, req.arguments).await
}
```

```typescript
// web/src/shared/api/mcpClient.ts — client mínimo
const client = new McpClient({ transport: "sse", url: "http://127.0.0.1:4848/mcp" });
await client.initialize();
const { tools } = await client.listTools(); // discovery dinámico
// tools = [{ name: "shell.fs.read", inputSchema: {...} }, ...]
const result = await client.callTool("shell.fs.read", { path: "web/src/App.tsx" });
```

> **Regla de oro:** si agregar un plugin requiere editar el router, tu arquitectura no escala. MCP hace que agregar un plugin sea correr un proceso que habla el protocolo — cero cambios en `desktop-app`.

## 5. Anti-patterns y limitaciones

| Anti-pattern | Por qué duele | Qué hacer en cambio |
|---|---|---|
| **`if path == "/shell/..."` por plugin** | Acople 1:1, cada plugin nuevo = código nuevo + redeploy | MCP discovery: el router es genérico, los plugins se registran |
| **Auto-discover sin allowlist** | Tool poisoning (ver MCPTox ASR 72.8%) | Allowlist + consentimiento del usuario por tool sensible (`fs.delete`, `pty.exec`) |
| **Sin validación de schema** | Args mal tipados → 400 en v2, o peor: ejecución incorrecta | `inputSchema` JSON Schema en cada tool; validar antes de `tools/call` |
| **MCP sin sandbox** | `tool_result` puede exfiltrar datos si el server es malicioso | Sandbox + validación de output + manifest firmada RSA |
| **Un solo transport para todo** | stdio no sirve para `hyper :4850` remoto | Elegí transport por caso: stdio para local, SSE/HTTP para remoto |

**Limitaciones de MCP (honestas):**

- **Overhead de protocolo:** handshake + validación añade latencia vs `probe()` TCP directo. Para 5 plugins locales, el `probe 250ms` crudo es más rápido que `initialize` MCP completo. Evaluá híbrido: probe rápido + MCP para invocación.
- **Ecosistema joven:** aunque donado a LF, la spec sigue evolucionando (2025-11-25 es la última estable). Breaking changes posibles.
- **Seguridad no resuelta por defecto:** MCP define el canal, no la política. Sin allowlist + vetting, es más riesgoso que tu `if` hardcodeado actual (que al menos es explícito).
- **No reemplaza buen ACI:** MCP resuelve discovery/invocación; el diseño del ACI (viewer paginado, edit con lint) sigue siendo tu responsabilidad (ver `04-swe-agent-aci-2024.md`).

## 6. Ejercicios prácticos

### Ejercicio 1 — MCP server mínimo en Rust (60 min)
1. Implementá un MCP server para `shell.fs.list` en `desktop-app/src/infrastructure/mcp/fs_server.rs` usando `rmcp` (Rust MCP SDK) o JSON-RPC manual.
2. Exponé `tools/list` con `inputSchema` y `tools/call` que delegue a `fsx::list_dir`.
3. Verificá con `npx @modelcontextprotocol/inspector` que el server se liste correctamente.

### Ejercicio 2 — Migración de un plugin (45 min)
1. Tomá `screenshots :3002` y envolvelo como MCP server que exponga `screenshots.capture` como tool.
2. Modificá `external_router.rs` para descubrirlo vía `initialize` en vez de `probe() 250ms` + `ureq`.
3. Medí latencia: `probe` crudo vs `initialize` MCP. Decidí si justifica híbrido.

### Ejercicio 3 — Allowlist y seguridad (30 min)
1. Implementá allowlist en `data/config.json`: `{ "mcp": { "allow": ["shell.fs.read", "shell.fs.list"], "deny": ["shell.fs.delete"] } }`.
2. Intentá `tools/call` con `shell.fs.delete` y verificá que se rechace antes de ejecutar.
3. Añadí regex scan sobre `description` de tools descubiertas (defensa MCPTox heurística <1.5s).
