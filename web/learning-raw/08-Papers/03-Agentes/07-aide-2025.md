## 1 Introducción — Qué problema resuelve

La mayoría de los agentes codean como un chat: `prompt → code → error → fix → error → fix...` appendeando historia infinita hasta que el contexto explota O(n²) o el agente se pierde. AIDE propone otra metáfora: **el espacio de soluciones es un árbol, no una línea**. Cada nodo es una solución completa y ejecutable (código + score); cada arista es un operador que propone una mejora sobre un nodo existente.

En lugar de "seguí chateando", AIDE hace `f(nodo) → nuevo código`, lo evalúa con tests/métricas reales y decide qué rama expandir. Sin historial infinito, sin prompt gigante: solo el árbol y una política de búsqueda (greedy, beam, etc.). Para vos, que tenés `ptyx :4849` donde el agente reintenta fixes linealmente y `opencode-stats` donde generás informes iterativamente, AIDE te muestra cómo mantener 3 ramas vivas en paralelo y quedarte con la mejor — en lugar de apostar todo a una sola línea de conversación.

## 2 Ideas clave

### 2.1 Árbol de soluciones — Cada nodo es código que corre

```
root (baseline / empty)
 ├─ nodo A (score 0.62) ─┬─ A1 (0.71) ── A1a (0.78) ← best
 │                       └─ A2 (0.65)
 ├─ nodo B (score 0.58) ── B1 (0.69)
 └─ nodo C (score 0.45) (podado)
```

- **Nodo:** código completo + score de evaluación + metadata (cómo se generó).
- **Operador `f(nodo) → nuevo código`:** es *stateless* — recibe un nodo y propone un parche/mejora. Puede ser "agregá regularización", "cambiá learning rate", "refactorizá esta función". El LLM es el operador.
- **Evaluación:** cada nodo se ejecuta y se scorea con métrica real (accuracy, tests pasando, lint). Sin score, no hay búsqueda.

### 2.2 Operador stateless — No appendees chat

La diferencia crucial con ReAct: el operador **no ve todo el historial**. Ve un nodo (código + score + feedback de evaluación) y propone el siguiente. Eso evita que el contexto crezca O(n²) y que el agente se ancle a errores viejos. Cada llamada es independiente y barata.

```ts
type SolutionNode = { id: string; code: string; score: number; parentId: string | null };
type Operator = (node: SolutionNode) => Promise<string>; // nuevo código

async function aideStep(node: SolutionNode, op: Operator): Promise<SolutionNode> {
  const newCode = await op(node);                    // LLM propone parche sobre node.code
  const result = await ptyx.exec(newCode);           // :4849 ejecuta
  const score = evaluate(result.stdout, result.exitCode); // tests / métrica
  return { id: crypto.randomUUID(), code: newCode, score, parentId: node.id };
}
```

### 2.3 Política de búsqueda — Qué rama expandir

AIDE no expande al azar. Usa políticas configurables:

| Política | Cómo elige nodo a expandir | Trade-off |
|---|---|---|
| **Greedy** | Siempre el mejor score | Rápido, pero puede quedar atrapado en óptimo local |
| **Beam (k=3)** | Top-k nodos vivos | Balance exploración/explotación |
| **Best-first** | Mejor score no expandido | Similar a A* sin heurística |
| **Diverse** | Mejor score + diversidad de código | Evita 3 ramas idénticas |

Podás ramas con score bajo o que no mejoran tras N expansiones.

## 3 Evidencia / Experimentos

| Benchmark | AIDE (GPT-4) | ReAct / single-shot | Delta |
|---|:---:|:---:|---|
| **Kaggle competitions (Weco)** | Medalla en 2/3 comps | 0/3 (ReAct lineal) | cualitativo |
| **MLE-Bench (75 tasks)** | **~16%** medal rate | ~8% (baseline) | 2× |
| **HumanEval (como search)** | 85%+ con beam k=3 | 67% single-shot | +18 pts |
| **Ablation sin árbol (solo lineal)** | — | cae ~40% en MLE-Bench | árbol importa |
| **Ablation sin evaluación** | — | cae ~50% (expande al azar) | score importa |

Setup: cada nodo es un script Python ejecutable (ML) o solución code; evaluación por métrica real (accuracy, pass@k) o tests. El paper enfatiza que la ganancia viene de **mantener múltiples hipótesis vivas** en lugar de apostar a una sola línea de chat que puede descarrilar irreversiblemente.

## 4 Cómo aplica a opencode-remote-android — Mapeo concreto

| Concepto del paper | Dónde lo usás / cómo implementarlo en el repo |
|---|---|
| **Árbol vs chat lineal** | Hoy tu `ptyx :4849` reintenta linealmente: `fix1 → fix2 → fix3` en el mismo chat. Con AIDE, mantené `fixA`, `fixB`, `fixC` como ramas paralelas y quedate con la que pasa `cargo check` / `tsc -b`. |
| **`opencode-stats :8765` e informes** | Generación de informes es búsqueda: cada nodo es un SQL/query + visualización + score (¿responde la pregunta?). Beam k=3 te da 3 informes candidatos; el user elige. No más "un intento y si falla, reintenta lineal". |
| **Operador stateless** | Cada `subagentTaskPart` puede ser un operador que recibe un nodo (código + score) y propone mejora. Stateless = no paga O(n²) por historial. Ver `web/src/shared/sse/handler.ts`. |
| **Evaluación automática** | Cada nodo se evalúa con `cargo check`, `tsc -b`, `pnpm test`, `cargo test` o métrica de negocio. Sin evaluación, el árbol no sabe qué podar. Integrá con `ptyx :4849` y `external_router`. |
| **Kanban como árbol** | Cada tarjeta en `kanban.json` puede tener `branches: SolutionNode[]` con `score` y `status: active|pruned|best`. `DesktopPanelRenderer` muestra las 3 mejores ramas side-by-side (como `DesktopGrid` col/resizer). |
| **Beam search en `DesktopGrid`** | Tus columnas/resizers ya soportan múltiples paneles. Usá esa UI para mostrar `beam k=3` ramas en paralelo — el user ve 3 intentos y elige, no espera un solo chat. |

```ts
// web/src/features/aide/tree.ts — árbol mínimo
type Node = { id: string; code: string; score: number; parentId: string | null; status: "active" | "pruned" | "best" };
class SolutionTree {
  nodes: Node[] = [{ id: "root", code: "// baseline", score: 0, parentId: null, status: "active" }];
  best(): Node { return [...this.nodes].sort((a, b) => b.score - a.score)[0]; }
  beam(k = 3): Node[] { return this.nodes.filter(n => n.status === "active").sort((a, b) => b.score - a.score).slice(0, k); }
  prune(threshold: number) { this.nodes.forEach(n => { if (n.score < threshold) n.status = "pruned"; }); }
  async expand(node: Node, operator: (n: Node) => Promise<string>, evaluate: (code: string) => Promise<number>) {
    const newCode = await operator(node);
    const score = await evaluate(newCode);
    this.nodes.push({ id: crypto.randomUUID(), code: newCode, score, parentId: node.id, status: "active" });
  }
}
```

## 5 Anti-patterns / Limitaciones

- **ReAct lineal sin ramificación.** Si tu agente solo hace `intento → error → fix → error → fix` en una sola línea, un error temprano contamina todo el resto. Un árbol te permite volver a un nodo bueno y probar otra rama — lineal no.
- **Operador que ve todo el historial.** Si tu operador recibe 200 mensajes de contexto en lugar de un nodo, pagás O(n²) y el LLM se ancla a errores viejos. Stateless es la gracia: un nodo + feedback, nada más.
- **Expandir sin evaluar.** Generar 10 ramas sin scorearlas es generar ruido. Cada nodo debe ejecutarse y scorearse antes de decidir si expandirlo o podarlo. Sin evaluación, el árbol crece sin dirección.
- **Beam demasiado ancho o estrecho.** `k=1` es greedy (óptimo local); `k=10` es caro (10× LLM calls por nivel). Para tu thin client, `k=2-3` es el sweet spot: diversidad sin fundir tokens.
- **Árbol sin límite de profundidad.** Un árbol que crece sin `max_depth` o `max_nodes` consume memoria y tokens infinito. Definí `max_depth=5`, `max_nodes=20` y `timeout` por evaluación.

## 6 Ejercicios prácticos (en tu repo)

1. **Árbol de 3 ramas para un fix.** Tomá un bug real de `web/src` o `desktop-app`. Generá 3 fixes distintos como nodos hijo de `root` (cada uno vía LLM con prompt distinto: "fix minimal", "fix con refactor", "fix con tests"). Evaluá cada uno con `tsc -b && cargo check` y quedate con el mejor score. ¿Supera el fix lineal single-shot?

2. **Beam k=3 para informes.** En `opencode-stats :8765`, ante la pregunta "¿qué sesiones consumieron más tokens esta semana?", generá 3 queries SQL distintas como 3 ramas, ejecutalas y mostrá las 3 en `DesktopGrid` side-by-side con su score (¿responde la pregunta? ¿es eficiente?). Dejá que el user elija.

3. **Kanban con branches.** Extendé `kanban.json` para que cada tarjeta tenga `branches: Node[]`. Al mover a "Doing", el agente genera 2 ramas iniciales; al fallar una, no la reintenta lineal: expande la otra. Visualizá el árbol en `DesktopPanelRenderer` como mini grafo (ver `opencode-stats` triple-GPU para inspiración).
